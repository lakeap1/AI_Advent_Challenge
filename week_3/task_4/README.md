# День 14 — инварианты помощника по теории арта

Помощник объясняет теорию арта и компьютерной графики: композицию, цвет, светотень, форму, перспективу и принципы формирования изображения. Конкретные программы обсуждаются по запросу пользователя. В учебном разборе он сам ведёт план с критериями и состояние задачи. Инварианты задают обязательные рамки: например, объяснять tangent-space normal map без изменения модели и UV. При обнаруженном конфликте приложение называет правило и отказывает, сохраняя прежнее состояние задачи.

Цель задания — хранить обязательные условия отдельно от диалога, передавать их модели и проверять запрос и ответ. Правила вводятся явно; предпочтения профиля не становятся инвариантами автоматически. Смысловую совместимость оценивает модель, поэтому безошибочное соблюдение произвольных правил не гарантируется.

Сохранены память, персонализация, этапы задачи, пауза, три стратегии контекста, политики и учёт расходов. Стек: Python, Flask, SQLite, прямой Responses API. Код самостоятельный, импортов из соседних заданий нет. Приложение рассчитано на одного локального оператора; профили изолируют пространства, но не заменяют аккаунты и авторизацию.

## Запуск

Python 3.11 или новее. Из папки задания:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Задайте `OPENAI_API_KEY` в `.env`, затем:

```powershell
.\.venv\Scripts\python.exe app.py
```

Откройте http://127.0.0.1:5014. Без ключа доступны редакторы, вызов модели завершится ошибкой. Модель `gpt-5.6-luna`, reasoning `none`, основной ответ до 1600 токенов. Поведение, политики и тариф — в `agent/config.toml`; инструкции смысловой проверки — в `AgentConfig`. Изменение конфигурации требует перезапуска.

## Правила и область действия

1. Выберите профиль и создайте задачу.
2. В панели «Что решение не должно нарушать» введите до пяти правил, по одному на строку; каждое до 500 символов.
3. Нажмите «Сохранить правила». Рядом появятся действующие правила, номера, ревизия и область.
4. Задайте вопрос. Несохранённый черновик на ответы не влияет.

Пример пяти правил для учебного разбора normal map (задаются пользователем, не включены автоматически):

```text
Сохранять tangent-space normal map и PBR-подход в этом разборе.
Не предлагать менять геометрию модели или UV-развёртку.
Не предлагать отключение normal map как окончательное решение; временное сравнение для диагностики допустимо.
Только теория и числовые примеры, без пошаговых действий в графическом редакторе.
Не утверждать, что файлы, сцена или рендер проверены: доступа к ним нет.
```

Правила принадлежат одной задаче внутри профиля. Все её диалоги и ветки используют один набор. Новая задача получает пустой набор даже в том же проекте. Смена профиля, отключение справочных слоёв, усечение истории, пауза и перезапуск не удаляют правила. Чат и автоматическое извлечение памяти не могут их менять.

Изменение правил — отдельное явное сохранение; пустой список снимает все правила. Устаревшая ревизия или чужие идентификаторы задачи/профиля отклоняются. Один сервер владеет папкой данных, выбор профиля общий для его вкладок; рекомендуется работать в одной вкладке.

## Примеры

Допустимый вопрос:

```text
На low-poly модели с PBR-материалом после подключения normal map появились заметные швы по границам UV, а на зеркальных участках освещение выглядит неправильным. Без normal map этих артефактов нет.

Как шейдер преобразует нормаль из текстуры в направление для расчёта освещения? Хочу разобраться в tangent space и понять, как последовательно отличить проблему запекания от ошибки импорта текстуры или расчёта тангентов.

Сцену сейчас не исправляем: это учебная задача. Хочу проверить понимание на числовом примере TBN, без работы в редакторе.
```

Конфликт с запретом отключать normal map как окончательное решение:

```text
Предложи полностью убрать normal map как окончательное решение проблемы.
```

При выявленном конфликте приложение возвращает `rejected`, точный номер и текст правила, объясняет недопустимость решения. Запрещённый совет не выдаётся после предупреждения. Просьба отменить правило через чат также проверяется как конфликт.

Теоретическое обсуждение другого подхода само по себе не запрещено:

```text
Чем object-space normal map отличается от tangent-space? Только теория, подход задачи не меняем.
```

Проверяющий различает теоретическое обсуждение и предложение изменить решение проекта по инструкции. Совпадение слова не считается программным доказательством нарушения. После отказа можно продолжать допустимую работу.

## Проверка и порядок обработки

При непустом наборе правил:

1. Локальная input policy проверяет непустой корректный UTF-8-текст и предел длины. Известное нарушение останавливает работу без API.
2. Отдельный вызов модели проверяет смысл текущего запроса в контексте и возвращает JSON-вердикт по каждому правилу.
3. Основной вызов получает актуальные правила в `TASK_INVARIANTS`, профиль, состояние и выбранную память. Правила имеют приоритет над просьбой в чате и предпочтениями.
4. Основной вызов запрашивает JSON через `text.format: json_object`. Код отдельно проверяет событие, цитату-основание, поля задачи и план: JSON-режим сам по себе не проверяет эту схему и смысл. Следующий этап вычисляется по таблице переходов Python. Для plan_ready и обычных сообщений этапов execution/validation отдельный вызов оценивает готовность этапа по цели, плану, текущему сообщению и прежним результатам. Ответ основного генератора не служит ему доказательством. Проверка output-инвариантов оценивает весь предлагаемый результат — ответ, план, цель, шаг, заметки и отчёт готовности — до их применения.
5. Только после принятия готовятся операции памяти и, для Facts, новый словарь. Состояние и извлечённая память сохраняются одной транзакцией; затем фиксируются Facts и пользовательский ответ. Служебный JSON-конверт в чат не выводится.

Код проверяет полный список известных уникальных ID, только логические значения, отсутствие лишних полей и повторных JSON-ключей. Ошибка формата, незавершённый ответ или недоступность проверяющего блокируют выдачу. Скрытых повторов и автоматического исправления нет. Отвергнутый кандидат не сохраняется как assistant message и не показывается в журнале.

При конфликте рабочая и долговременная память, Facts, принятые решения и состояние остаются прежними. Попытка запроса и метаданные вызовов сохраняются. Сбой служебной обработки памяти после успешной проверки тоже останавливает выдачу.

Без правил используется тот же порядок проверки автомата, готовности этапов и отложенного сохранения, но без двух проверок инвариантов. Ответ использует память предыдущего принятого хода и текущий вопрос; новые записи появляются после принятия результата. Невалидный машинный ответ отклоняется до извлечения памяти.

## Состояние, профиль и память

Этапы: `planning → execution → validation → done`, возвраты `execution → planning` и `validation → execution`. Модель предлагает событие разговора, а Python проверяет его допустимость и вычисляет следующий этап. Пользователь обсуждает задачу в чате; панель состояния доступна только для чтения. Ручные действия — пауза и продолжение.

События: `plan_ready` переводит планирование в выполнение, `result_reported` — выполнение в проверку, `finish` — проверку в завершение. `revise_plan` возвращает к планированию, `revise_work` — к выполнению; `stay` сохраняет этап. Для перехода требуется точная цитата из текущего сообщения пользователя. Цитата подтверждает наличие текста, но не доказывает правильность его интерпретации моделью.

План содержит от одного до шести шагов, у каждого действие и критерий проверки. Перед выполнением отдельный проверяющий должен подтвердить полноту и проверяемость плана; при уточнении в planning он может быть пустым. В execution и validation цель и план зафиксированы: для их изменения нужен возврат к планированию через revise_plan, который очищает прежний план и результаты.

В step_results для каждого шага сохраняются статус pending/passed/failed, конкретный результат, цитата из сообщения и причина оценки. Новый passed или failed требует буквальной цитаты из текущей реплики; прежний подтверждённый результат переносится без повторной цитаты. К проверке результата можно перейти только после passed по всем шагам, к done — дополнительно после подтверждения пользователя. Для теории арта результатом может быть решённый пример или объяснение пользователя; работа в редакторе не обязательна. Общая фраза «готово» и решение, предложенное самим ассистентом, не считаются достаточным доказательством.

Если инварианты соблюдены, но переход преждевременен, приложение возвращает stage_not_ready: этап, цель, план и обычные поля остаются прежними, но проверенные результаты шагов и причина недопуска сохраняются. Ответ кандидата, рабочая память и Facts не принимаются. Это отличается от конфликта инвариантов или ошибки отчёта: при них даже частичный прогресс не записывается. Панель показывает состояние каждого шага и итог последней проверки.

План, цель, шаг, ожидание, заметки и результаты сохраняются независимо от истории. Миграция добавляет отсутствующие поля plan, step_results и validation без сброса этапа, паузы, правил и сообщений. Старые планы получают pending, а не выдуманное подтверждение выполнения; сохранённые ранее done не переоцениваются автоматически. Для старой validation без плана предусмотрен возврат revise_work, затем revise_plan.

Пауза останавливает новые запросы до явного продолжения, но не отменяет уже отправленный вызов API. Завершённая задача не принимает новые вопросы. Предложение выполнить действие не является доказательством его выполнения: помощник ждёт сообщения пользователя.

Профиль хранит стиль, формат (`plain`, `steps`, `markdown`) и личные предпочтения отдельно от истории. Перед каждым ответом агент читает актуальный профиль и подставляет только выбранное правило оформления: обычный текст, нумерованные шаги или Markdown с коротким заголовком второго уровня и списком. При выбранном Markdown общего запрета разметки в инструкции нет; интерфейс показывает разметку как текст. Для нейтрального профиля используются абзацы без Markdown; явная просьба текущего сообщения может временно изменить стиль или формат.

Инструкция учитывает аудиторию, предел слов и личные ограничения, но соблюдение этих предпочтений оценивает сама модель: программной проверки объёма и оформления нет. Личное ограничение отменяется только явным указанием пользователя, а обязательные инварианты задачи имеют приоритет над профилем и запросом и меняются только в отдельной панели. Служебное извлечение памяти, Facts, проверки готовности и инвариантов сохраняют JSON независимо от выбранного оформления ответа.

Sliding Window передаёт последние 6 сообщений; Facts добавляет словарь фактов; Branching сохраняет контрольные точки и ветки. Правила и состояние не обрезаются вместе с историей. Ветки разделяют рабочую память и правила своей задачи; независимые ограничения требуют другой задачи.

Хранилища:

- `data/profiles.sqlite3` — каталог и выбранный профиль.
- `data/profiles/<id>/memory.sqlite3` — задачи, диалоги, профиль и память; отдельные таблицы `task_states` и `task_invariants`.
- `data/profiles/<id>/dialogue-<id>.sqlite3` — сообщения, ветки и журнал вызовов с точными снимками правил и вердиктами.

`task_invariants` — единственный источник текущих правил; снимки журнала объясняют прошлые запросы. Данные и `.env` исключены из Git. Другую папку задаёт `CHAT_DATA_DIR`; прежние базы автоматически не импортируются.

## Токены и стоимость

Для каждого вызова сохраняются фактические input/output/total tokens, cached input, cache write и reasoning при наличии, стоимость USD, модель, тариф, режим и результаты политик. Reasoning входит в output; кеш не оплачивается дважды. Трасса показывает использованную ревизию правил и вердикты.

Успешный вопрос с правилами требует 4 вызова без проверки готовности этапа или 5 с ней; Facts добавляет ещё один. Входной отказ обычно расходует только один вызов проверяющего инвариантов, выходной — 3 или 4 вызова. Проверка готовности отображается отдельно как validation; её лимит — 2400 выходных токенов, отдельные input/output policies заданы в конфигурации. При stage_not_ready извлечение памяти и обновление Facts не вызываются. Основной запрос при входном отказе помечен как не вызванный; проверка учитывается отдельно и входит в сумму. Неизвестные расходы не превращаются в ноль, сумма отмечается неполной. Доступный usage сохраняется до разбора вердикта; прерванные запросы не повторяются.

Тариф и дата проверки находятся в конфигурации; источник — [описание модели](https://developers.openai.com/api/docs/models/gpt-5.6-luna). Расчёт применим к указанной модели, режиму и диапазону входа; это оценка, не счёт провайдера.

## Ограничения

- Смысловая оценка вероятностная: возможны пропуск нарушения, необоснованный отказ, влияние неоднозначных правил и инструкций в данных. Успешные примеры не доказывают всеобщее соблюдение.
- Числовые, архитектурные и технические условия в свободном тексте не становятся формально доказанными. Код гарантирует область, ревизию, формат данных, порядок обработки и блокировку отвергнутого результата.
- Приложение не управляет графическими редакторами, не открывает сцену, не рендерит и не проверяет изображение. Пользователь сам выполняет и подтверждает действия. Автомат сохраняет сведения из разговора, не проверяя фактическую работу в редакторе.
- Базы не зашифрованы. Состояние и извлечённая память имеют общую транзакцию, но журнал и Facts находятся в другой SQLite-базе. Физическая авария между фиксациями двух баз может оставить несогласованные записи; общей аварийной атомарности этих баз нет.

## Проверки и файлы

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты используют подставной транспорт: scope, ревизии, восстановление, входные/выходные отказы, отсутствие утечек, порядок вызовов, готовность этапов, частичный прогресс, запрет подмены критериев, продолжение и расходы при прерывании. Качество реальной смысловой оценки ими не проверяется; реальные запросы оплачиваются отдельно.

- `app.py`, `profiles.py`, `workspace.py` — HTTP и рабочие пространства.
- `agent/invariants.py`, `guarded.py` — правила, вердикты и защищённый цикл.
- `agent/core.py`, `config.py`, `config.toml` — агент, конфигурация и политики.
- `agent/task_state.py`, `task_protocol.py`, `task_plan.py`, `task_validation.py` — состояние, события автомата, план и независимая проверка готовности.
- `agent/personalization.py`, `memory.py`, `extraction.py` — профиль и память.
- `agent/storage.py`, `facts.py`, `tokens.py`, `usage.py`, `transport.py` — история, контекст, учёт и API.
- `templates/`, `static/` — интерфейс; `tests/` — проверки.
- `requirements.txt`, `pytest.ini`, `.env.example`, `.gitignore` — настройка.

# День 13 — состояние задачи помощника по графике и арту

Помощник объясняет материалы, свет, моделирование, композицию и другие вопросы компьютерной графики. Формальное состояние задачи сохраняет этап, текущий шаг и ожидаемое действие. После паузы и перезапуска можно продолжить с прежнего места. Сохранены краткосрочная, рабочая и долговременная память, профиль, стратегии контекста, политики и учёт расходов.

Приложение локальное: Python, Flask, SQLite, прямое обращение к Responses API. Код задания самостоятельный, импортов из соседних заданий нет. Именованные профили — отдельные локальные рабочие пространства одного оператора; аккаунтов и авторизации нет.

## Запуск

Python 3.11 или новее. Из папки задания:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

В `.env` задайте `OPENAI_API_KEY`, затем:

```powershell
.\.venv\Scripts\python.exe app.py
```

Откройте http://127.0.0.1:5013. Без ключа работают интерфейс и редакторы, отправка модели вернёт ошибку. Конфигурация находится в `agent/config.toml`: модель `gpt-5.6-sol`, reasoning `medium`, предел основного ответа 1600 токенов. Изменение конфигурации требует перезапуска.

## Автоматическое состояние задачи

Опишите проблему в чате. Агент сам формулирует цель, ведёт шаг, ожидаемое действие и заметки, а приложение сохраняет их после каждого принятого ответа. Редактировать карточку и выбирать этап кнопкой не требуется. Панель показывает результат работы автомата.

Сам автомат реализован в Python: модель определяет событие разговора, а код вычисляет следующий этап по таблице. Модель не задаёт `stage` или `paused` напрямую.

| Текущий этап | Событие | Следующий этап |
|---|---|---|
| Планирование | План готов (`plan_ready`) | Выполнение |
| Выполнение | Получен результат (`result_reported`) | Проверка |
| Выполнение | Нужен новый план (`revise_plan`) | Планирование |
| Проверка | Нужна ещё попытка (`revise_work`) | Выполнение |
| Проверка | Пользователь подтвердил результат или завершение (`finish`) | Завершено |
| Любой незавершённый | Уточнение или ожидание (`stay`) | Тот же этап |

Перед переходом в выполнение агент составляет план: от одного до шести упорядоченных шагов, у каждого действие и критерий проверки (до 500 символов на поле). Код проверяет структуру и непустые поля. Отдельный вызов проверяющего оценивает, покрывает ли план цель и проверяемы ли критерии. Только после положительного заключения план сохраняется атомарно с этапом. Одного события `plan_ready` без корректного плана недостаточно: ответ будет отклонён, состояние сохранится, расходы вызова учтутся без скрытого повтора. Критерии после начала выполнения зафиксированы: менять их можно только через возврат к планированию.

Карточка «План и критерии» показывает сохранённую последовательность. План передаётся в следующие запросы независимо от окна сообщений. В планировании допустим пустой план, если требуется уточнение; возврат `revise_plan` очищает прежний план. Следующие принятые ответы в выполнении, проверке и завершении обязаны сохранять непустой план. Ручной записи полей и переключения этапов нет; доступны только пауза и продолжение. Отдельное ручное утверждение не требуется: план и первое действие могут появиться в одном ответе.

Пример технического вопроса по графике:

```text
На low-poly модели с PBR-материалом после подключения normal map появились заметные швы по границам UV, а на зеркальных участках освещение выглядит неправильным. Без normal map этих артефактов нет.

Как шейдер преобразует нормаль из текстуры в направление для расчёта освещения? Хочу разобраться в tangent space и понять, как последовательно отличить проблему запекания от ошибки импорта текстуры или расчёта тангентов.
```

Помощник может уточнить исходные знания, затем составить план объяснения, разбора примера и проверки понимания. Сообщите свой разбор примера с результатами по каждому пункту — после проверки всех критериев агент сможет перейти к проверке итоговой цели; подтвердите, что цель достигнута, чтобы завершить задачу. По одному сообщению выполняется не более одного перехода. Точные формулировки и необходимость уточнений зависят от ответа модели.

Существующие базы автоматически получают пустое поле плана без сброса прежнего этапа, паузы и истории. При следующем ответе агент должен восстановить план по сохранённому контексту или, из выполнения, вернуться к планированию при нехватке данных. Для отката к версии приложения без этого поля нужна совместимая резервная копия базы.

У каждого шага сохраняются статус (ожидает результата / выполнен / не выполнен), конкретный результат, точная цитата пользователя и причина оценки. Проверяющий получает текущий текст, цель, план и предыдущие проверенные результаты, но не ответ основного помощника. Новые подтверждения требуют цитаты из текущего сообщения. При неполном результате переход блокируется, а корректно подтверждённый частичный прогресс сохраняется. Пример: после выполнения одного из трёх шагов состояние останется «Выполнение», карточка покажет «Подтверждено 1 из 3» и недостающие шаги.

Завершение планирования требует пригодного плана; завершение выполнения — статуса «выполнен» у каждого шага; завершение проверки — всех выполненных критериев и явного подтверждения результата пользователем. Возврат к планированию очищает план и прогресс, новая попытка выполнения сбрасывает прежние результаты. Старые задачи получают неподтверждённые шаги: миграция не приписывает им выполненную работу. Задачу без сохранённого плана нужно вернуть к планированию.

Смысл результата и его соответствие критерию оценивает отдельный вызов модели. Код проверяет полноту отчёта, точность цитат, сохранность критериев и обязательные условия перехода. Проверяющий может ошибиться: наличие цитаты не доказывает истинность сообщённого. Агент не управляет Blender, не видит сцену и не запускает шейдер. Для учебной задачи проверяется предоставленный разбор или расчёт; для внешней работы — сообщённые наблюдения.

Модель возвращает машинный JSON-конверт с ответом и обновлением задачи. В чате отображается только текст `answer` с выбранным форматом профиля. Некорректный конверт или запрещённое событие отклоняются без изменения состояния и успешного ответа; токены и стоимость учитываются, скрытого повторного вызова нет. Дополнительная проверка выполняется перед выходом из планирования и на сообщениях в выполнении и проверке, кроме возвратов на предыдущий этап. Её токены и стоимость входят в сумму чата отдельной строкой «Проверка этапа». Ошибка, отказ или некорректный отчёт проверяющего останавливают обработку без изменения состояния и без скрытого повтора. Снимки до/после, событие и цитата сохраняются в метаданных основного запроса.

«Пауза» и «Продолжить» доступны на незавершённых этапах и не вызывают модель. На паузе чат заблокирован, сохранённый шаг не меняется. Пауза не отменяет уже отправленный синхронный запрос: интерфейс занят до его завершения. В done новые вопросы и команды паузы/продолжения отклоняются; новую работу начинайте отдельной задачей.

После перезагрузки страницы, перезапуска приложения и открытия нового диалога той же задачи можно спросить «Что сделать сейчас?» без повторения цели и заметок. Состояние хранится в таблице `task_states` базы `memory.sqlite3` выбранного профиля отдельно от истории. Диалоги и ветки одной задачи разделяют одно состояние, переключение ветки не откатывает этап. Для независимого процесса создавайте отдельную задачу.

Блок `TASK_STATE` передаётся независимо от переключателей справочных слоёв. Служебные JSON-запросы памяти и Facts сохраняют собственный контракт и не выполняют переходы. Обновления состояния и история находятся в разных SQLite-базах: авария между записями может оставить новый этап без завершённой записи ответа. Одновременные серверы с одними данными не поддерживаются.

## Профиль и использование

При первом запуске создаётся нейтральный профиль «Основной». Его настройки не считаются известными предпочтениями реального пользователя.

- Стиль: свободный текст, например «Объясняй термины простыми словами, до 100 слов».
- Формат: обычный текст с абзацами (`plain`, по умолчанию), нумерованные шаги без Markdown (`steps`) или явно выбранный Markdown (`markdown`).
- Ограничения: например «Blender/Cycles, без платных аддонов и новых текстур».

Стиль и ограничения допускают пустую строку и до 1000 символов. Все три поля сохраняются вместе: неверное поле отменяет всю операцию. В панели отдельно видны действующие настройки и редактируемый черновик. Для сравнения можно явно создать демонстрационные профили новичка и опытного пользователя.

Выбор профиля действует на все его задачи и диалоги. Другой профиль имеет отдельные сообщения, рабочую память, решения, ветки и расходы. Возвращение восстанавливает прежнее состояние. Выбор общий для вкладок одного запущенного приложения: работайте в одной вкладке либо обновляйте состояние после переключения в другой. Одновременные серверы с одной папкой данных не поддерживаются.

## Память и восстановление

`data/profiles.sqlite3` хранит идентификаторы, имена и выбор. В `data/profiles/<id>/memory.sqlite3` находятся задачи, диалоги, рабочая и долговременная память. `dialogue-<id>.sqlite3` хранит историю, ветки и метаданные расходов конкретного диалога.

Предпочтения представлены версионными записями прежней модели памяти: слой `long_term`, категория `profile`, область `user`, ключи `personalization.style`, `personalization.format`, `personalization.constraints`. Второй копии значений в каталоге нет. Редактор создаёт закреплённые версии; общие команды памяти не могут удалять, переносить или разблокировать их. Старые версии остаются для объяснения прежних запросов.

В этом задании профиль управляется явно: чат не переписывает настройки. Автоматическое извлечение продолжает сохранять условия задачи, устойчивые решения и знания. Предложения модели категории `profile` пропускаются с причиной в метаданных служебного запроса. Устойчивую информацию, которую требуется учитывать как личное предпочтение, внесите в редактор.

Смена задачи сохраняет профиль и меняет рабочую память. Новый диалог той же задачи начинает пустую историю с её рабочей памятью. Решения проекта доступны только задачам с тем же проектом внутри выбранного профиля. После обновления страницы и перезапуска восстанавливаются выбор, предпочтения и диалоги. Для другой папки данных задайте `CHAT_DATA_DIR`. Прежние базы автоматически не импортируются.

Данные и `.env` исключены из Git. Тексты сохраняются для истории и памяти; учёт расходов не создаёт дополнительную копию переписки. Базы не зашифрованы. Каталог, память и журнал находятся в разных SQLite-базах без общей транзакции: авария между сохранением памяти и завершением журнала может оставить обновлённую память при interrupted-запросе с неизвестным расходом.

## Автоматическое применение и приоритеты

Перед каждым пользовательским вызовом агент читает актуальный профиль. Сборщик подставляет в `instructions` только выбранное правило оформления, затем добавляет стиль, ограничения и сохранённое состояние задачи. Общего запрета Markdown при выбранном Markdown нет. Для нейтрального профиля используется обычный текст. Далее передаются выбранные записи памяти, Facts при соответствующей стратегии и сообщения диалога. Профиль применяется даже при отключении справочных слоёв и учитывается в оценке размера запроса.

Приоритет, заданный модели: правила приложения и политики → явная инструкция текущего запроса → актуальный профиль → прежние пожелания из истории и памяти. Просьба «для этого ответа используй обычный текст» временно заменяет Markdown-профиль, сохраняя настройки. При неясном конфликте личных ограничений модель получает инструкцию уточнить намерение.

Извлечение памяти и обновление Facts сохраняют собственные JSON-инструкции. Пользовательский формат к ним не применяется. Дополнительного API-вызова ради персонализации нет. Скрытые повторы и исправление ответа ради соответствия профилю не выполняются.

«Состав запроса» показывает идентификатор профиля и точные использованные версии. После редактирования старая трасса показывает прежние значения. Это доказательство переданного контекста, а не гарантия выполнения всех пожеланий моделью.

## Стратегии контекста

- Sliding Window: последние 6 отдельных сообщений, включая вопрос; вся история остаётся на диске.
- Facts: дополнительный вызов обновляет словарь фактов диалога, передаваемый вместе с последними 6 сообщениями. Он не заменяет рабочую память или профиль.
- Branching: checkpoint и независимые продолжения истории. Рабочая память общая для задачи и её веток; независимые условия требуют другой задачи.

Профиль не обрезается вместе с историей. Сохраняются стратегии дня 10 и модель памяти дня 11; отдельный эксперимент со summary дня 9 остаётся в своём задании. Branching допускает рост истории до ошибки лимита API без скрытого сжатия. Предпросмотр оценивает текст до извлечения, не равен usage API и не гарантирует попадание в окно.

## Пример сравнения

Создайте два различных профиля с одинаковой стратегией и новыми задачами без истории. Задайте один вопрос, не перечисляя предпочтения:

```text
Почему керамический материал выглядит пластиковым и что проверить первым?
```

Сравните объяснение терминов, порядок шагов, формат и соблюдение ограничений. Простая разница формулировок ничего не доказывает. Затем спросите «Как проверить это одним пробным рендером?», измените настройку и отправьте следующий вопрос без её повторения. Сверьте автоматическую передачу по трассе.

## Политики, токены и стоимость

Input policy проверяет непустой корректный UTF-8-текст и предел длины до API. Output policy требует завершённый непустой ответ корректной структуры без отказа; служебные ответы дополнительно проверяются по машинному контракту. Отклонённый ответ не выдаётся как успешный.

Смысл, стиль, число слов и Markdown задаются инструкцией, программно не гарантируются. Выбранный Markdown требует короткого заголовка второго уровня и списка; интерфейс показывает текст ответа с исходной разметкой. Reasoning расходует выходные токены вместе с видимым ответом; слишком малый max_output_tokens может дать incomplete, такой ответ отклоняется без повтора. Приложение не открывает сцены, не выполняет рендер и не анализирует изображения; советы остаются рекомендациями.

Каждый вызов сохраняет фактические input/output/total tokens, cached input, cache write и reasoning при наличии, USD-стоимость, модель, режим, тариф и результаты политик. Сумма диалога включает служебные вызовы и отклонённые ответы с известным usage. Reasoning входит в output и не оплачивается повторно; кеш не учитывается дважды. Неизвестные расходы остаются неизвестными, сумма отмечается неполной. Прерванные запросы не повторяются автоматически.

Тариф и дата проверки указаны в конфигурации со ссылкой на [описание модели](https://developers.openai.com/api/docs/models/gpt-5.6-sol). Расчёт применим к указанной модели, стандартной обработке и поддержанному диапазону входа; это оценка, не счёт провайдера.

## Проверки и файлы

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты используют подставной транспорт: проверяют хранение, переключение, восстановление, атомарность, версии, payload всех стратегий, служебные JSON, политики и расходы. Смысл реальных ответов ими не проверяется; реальные API-вызовы оплачиваются отдельно.

- `agent/task_state.py`, `agent/task_protocol.py`, `agent/task_plan.py`, `agent/task_validation.py` — хранение, события автомата, проверка плана и машинного ответа, контекст этапа.
- `agent/personalization.py`, `memory.py`, `extraction.py` — профиль и память.
- `agent/core.py`, `config.py`, `config.toml` — агент, поведение и политики.
- `agent/storage.py`, `facts.py`, `tokens.py`, `usage.py`, `transport.py` — история, контекст, учёт и API.
- `templates/`, `static/` — интерфейс.
- `tests/`, `pytest.ini`, `requirements.txt`, `.env.example` — проверки и настройка.

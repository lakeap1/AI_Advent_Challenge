# День 15 — контролируемые этапы помощника по арту

Помощник объясняет компьютерную графику и теорию арта: композицию, цвет, светотень, форму, материалы и принципы формирования изображения. Он помогает пройти учебную задачу от плана до проверки понимания. Конкретные редакторы и технические настройки обсуждаются по запросу пользователя.

Цель задания — контролировать допустимые переходы и условия их выполнения. Планирование, выполнение, проверка и завершение хранятся отдельно от переписки. Модель предлагает событие, а приложение проверяет его по таблице переходов, сохранённому плану и отдельному отчёту проверки.

Сохранены инварианты, память, персонализация, пауза, три стратегии контекста, политики и учёт расходов. Стек: Python, Flask, SQLite и прямой Responses API. Код развивает предыдущую версию помощника и находится целиком в этой папке; импортов из соседних заданий нет.

## Запуск

Требуется Python 3.11 или новее. Из папки задания:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Укажите `OPENAI_API_KEY` в `.env`, затем:

```powershell
.\.venv\Scripts\python.exe app.py
```

Откройте http://127.0.0.1:5015. Без ключа доступны локальные редакторы, но модель не ответит. Настройки модели, политик и тарифа — в `agent/config.toml`. По умолчанию используется `gpt-5.6-luna`, reasoning `none`. После изменения конфигурации перезапустите приложение.

Данные сохраняются в `data/`; другой каталог задаётся переменной `CHAT_DATA_DIR`. Приложение рассчитано на одного локального оператора. Профили разделяют пространства, но не заменяют аккаунты и авторизацию.

## Работа с задачей

1. Опишите цель в чате. Помощник уточнит условия и покажет план с действиями и проверяемыми критериями. Карточка «Где остановились» отображает сохранённые данные.
2. Явно утвердите показанный план отдельным сообщением, например «Утверждаю план». Можно выразить принятие другими словами. Если одновременно изменить цель или критерии, сначала нужен новый план и его утверждение.
3. Выполните упражнение или внешние действия и сообщите конкретный результат каждого шага. Помощник объясняет действия, но не управляет редактором.
4. Сопоставьте результаты с критериями и явно примите итог. Только после успешной проверки задача завершится.

Пример начала учебного разбора:

```text
Хочу понять, почему большой источник света даёт мягкую тень. Составь короткий план: объяснение и проверка моего понимания на одном примере. Без работы в редакторе.
```

Затем можно утвердить план, получить объяснение и своими словами разобрать пример. «Готово», «потом проверю» или просьба пропустить проверку не заменяют результаты по критериям.

## Этапы и условия

| Переход | Что требуется |
|---|---|
| Планирование → Выполнение | Ранее сохранённый непустой план с критериями; неизменённые цель и план; явное утверждение пользователя; отдельная положительная проверка готовности |
| Выполнение → Проверка | Актуальное утверждение плана; подтверждённый результат по каждому шагу |
| Проверка → Завершено | Актуальное утверждение плана; все критерии пройдены; пользователь явно принимает итог |
| Выполнение → Планирование | Пересмотр цели или плана; прежний план, утверждение и результаты сбрасываются |
| Проверка → Выполнение | Нужна доработка; план и утверждение сохраняются, результаты и проверка сбрасываются |

Обычное сообщение может оставить этап прежним. Прямой переход из планирования в завершение и неизвестное событие запрещены. API не предоставляет прямое редактирование этапа, цели и плана: ручные действия — пауза и продолжение. Подмена машинного ответа не обходит проверки хранилища.

При утверждении сохраняются цитата пользователя и отпечаток цели со всеми шагами и критериями. Переходы требуют соответствия этому отпечатку. Отчёт проверки привязан к актуальному входу: цели, плану, прежним результатам и текущему сообщению. Устаревший отчёт не принимается.

При отказе приложение объясняет причину и необходимое действие. Предложенные моделью этап, шаг и заметки не записываются. Отдельный корректный отчёт может сохранить уже подтверждённые частичные результаты, оставив этап прежним: это позволяет закончить остальные шаги. При конфликте инвариантов даже частичные результаты не сохраняются.

## Что означает проверка

Проверяющий запрос модели сопоставляет сообщение пользователя с каждым критерием плана. Для нового успешного или неуспешного результата нужны конкретное описание и точная цитата текущего сообщения. Ответ основного генератора не служит доказательством выполнения упражнения. Прежние результаты берутся из сохранённого состояния; новые противоречащие сведения могут изменить их оценку.

Для теоретической задачи результатом может быть объяснение своими словами, решение числового примера или обоснованное сравнение. Для работы в редакторе источником сведений служит отчёт пользователя. Приложение не открывает изображения, сцены или файлы и не подтверждает их качество самостоятельно.

Код проверяет допустимый этап, форму отчёта, полный набор шагов, цитаты и связь с актуальными данными. Смысл утверждения, правильность объяснения и совместимость с произвольными правилами оценивает модель. Эти оценки могут ошибаться: формально корректный отчёт не доказывает фактическую правильность художественного результата.

## Пауза и продолжение

«Поставить на паузу» сохраняет этап, шаг, ожидание, план, утверждение и результаты. Чат блокируется и на сервере. Обновление страницы и перезапуск приложения с тем же каталогом данных сохраняют паузу. «Продолжить» возвращает к сохранённому месту без повторного описания задачи.

Завершённая задача терминальна: продолжить её как активную нельзя. Создайте новую задачу. Старые задачи из версии без утверждения плана не получают фиктивного согласия при обновлении: вернитесь к пересмотру плана и утвердите его заново. Из этапа проверки сначала требуется возврат к выполнению.

## Инварианты, профиль и память

В панели правил задаются 5–8 обязательных условий текущей задачи; пустой список отключает смысловые проверки инвариантов. Правила хранятся отдельно с ревизией, одинаковы во всех диалогах задачи и не смешиваются с другой задачей или профилем. Редактирование правил — явное действие в панели; чат их не переписывает. Переходы и пауза не отменяют правила. Предпочтения профиля не становятся инвариантами автоматически.

Непустой список добавляет проверки входа и предлагаемого результата. При конфликте ответ не публикуется, состояние, рабочая и долговременная память сохраняются. Неверный или неполный вердикт также останавливает обработку; скрытых повторов нет.

История диалога, рабочая память задачи и долговременная память профиля сохраняются отдельно. Профиль задаёт стиль, формат и ограничения. Режимы контекста: Sliding Window, Sticky Facts и Branching. Отключение справочных слоёв не отключает профиль, состояние и правила. Обычный ответ по умолчанию запрашивается текстом с абзацами без Markdown; другой формат можно явно выбрать в профиле или запросе. Машинный JSON-конверт не показывается в чате.

## Токены, стоимость и политики

Журнал показывает фактические `input_tokens`, `output_tokens`, `total_tokens` каждого API-вызова, USD и накопленную стоимость диалога. В неё включены основной ответ, проверки готовности и инвариантов, извлечение памяти и обновление Facts. Cached input и reasoning показываются отдельно, если они присутствуют; reasoning уже входит в output и повторно не оплачивается.

Модель, режим обслуживания, тариф, источник и дата сохранены в метаданных. Неизвестные usage или стоимость обозначаются неизвестными; неполная сумма не выдаётся за точную. Отказ без API отличается от выполненного вызова с неизвестными расходами. Расход отклонённого ответа сохраняется.

Input policy проверяет непустой текст, корректность UTF-8 и длину до вызова модели. Output policy проверяет завершённый текстовый ответ; дополнительно проверяются машинные схемы и условия переходов. Это не детерминированная проверка произвольного смысла или художественного качества.

Состояние задачи и извлечённая память сохраняются одной транзакцией. Журнал и Facts находятся в отдельной SQLite-базе: физическая авария между фиксациями двух баз может оставить несогласованные записи. Базы локальны и не зашифрованы.

## Проверки и состав файлов

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Автоматические тесты используют подставной транспорт. Проверяются переходы и отказы, актуальность утверждения и отчёта, пауза и повторное открытие SQLite, изоляция правил, память, политики и расходы. Они не измеряют качество реальной смысловой оценки модели.

- `app.py`, `profiles.py`, `workspace.py` — HTTP и рабочие пространства.
- `agent/core.py`, `config.py`, `config.toml` — агент, настройки и политики.
- `agent/task_state.py`, `task_protocol.py`, `task_plan.py`, `task_validation.py` — автомат, хранение, утверждение и проверка.
- `agent/invariants.py`, `guarded.py` — инварианты и порядок принятия результата.
- `agent/personalization.py`, `memory.py`, `extraction.py` — профиль и память.
- `agent/storage.py`, `facts.py`, `tokens.py`, `usage.py`, `transport.py` — история, контекст, учёт и API.
- `templates/`, `static/` — интерфейс; `tests/` — проверки.
- `requirements.txt`, `pytest.ini`, `.env.example`, `.gitignore` — установка и настройка.

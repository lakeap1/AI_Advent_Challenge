# День 24 — ответы по источникам локальной базы

Помощник по компьютерной графике и арту продолжает функции профилей, памяти, задач, MCP, сводок, веток и журнала расходов. Основной чат теперь ищет фрагменты локальной базы, оценивает их полезность и отвечает через обычного агента. Содержательные блоки ответа имеют метки реально переданных фрагментов; раскрываемая карточка показывает исходный текст и локатор каждого использованного источника. Если материалов не хватает, помощник говорит «Не знаю» и просит уточнить вопрос. Ошибки API и индекса остаются ошибками.

Текущий индекс содержит документацию и код самого помощника. Он подходит для вопросов о его возможностях и реализации; материалов для произвольных вопросов по компьютерной графике там может не быть. Метка фрагмента доказывает происхождение текста, но сама по себе не доказывает, что пересказ модели верен по смыслу.

## Запуск

Нужны Python 3.11+ и ключ OpenAI. Из каталога `week_5/task_4`:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
# Заполните OPENAI_API_KEY в локальном .env.
.venv\Scripts\python.exe app.py
```

Основной чат открыт на `http://127.0.0.1:5024/`; страница `/indexing` управляет документами. `CHAT_DATA_DIR` задаёт каталог локальных SQLite-хранилищ вместо `data/`. Приложение не импортирует код предыдущих заданий при работе.

Перед вопросами нужен совместимый индекс. Его можно создать на странице индексации либо перенести штатной командой при остановленном сервере:

```powershell
.venv\Scripts\python.exe -B -m rag.cli import-index --source ПУТЬ_К_ПРОВЕРЕННОМУ_indexing.sqlite3 --data-dir data
```

Импорт проверяет модель и размерность embedding, состав корпуса, чанки и метаданные. Существующий индекс не перезаписывается. Если исходный корпус изменился, индекс нужно создать заново из актуальных документов. Сервер и команду импорта не запускают параллельно для одного хранилища.

## Ответы, источники и расходы

Основной `/api/ask` всегда использует фильтр. Поиск сохраняет до 20 кандидатов: 40% мест занимают лидеры по косинусному сходству, остальные заполняются по объединённому рангу векторного поиска и документного BM25 (RRF, k=60). Лексическая прибавка применяется только к лучшему по векторному рангу чанку каждого файла; тексты документов для BM25 восстанавливаются из проверенных чанков индекса без дополнительного обращения к API. Если лексических совпадений нет, сохраняется векторный порядок. Затем модель оценивает кандидатов по шкале 0–3; при пороге 2 в контекст попадают до 6 неперекрывающихся фрагментов в пределах 6000 UTF-8 байт. Клиентский флаг не отключает этот маршрут. Шкала релевантности порядковая, не вероятность. Отбор не восстановит нужный факт, если он отсутствует среди кандидатов или в корпусе.

Модель возвращает внутреннюю структуру утверждений с метками источников. Приложение принимает только известные метки из отправленного контекста, собирает обычный текст ответа и показывает только использованные фрагменты с `source`, `section`, `chunk_id` и полным текстом. Кандидаты и выбранный контекст сохраняются отдельно для аудита в журнале поиска. Дословная цитата в ответе не требуется. Смысловую поддержку пересказа проверяют отдельно.

Input policy останавливает недопустимый запрос до API. Output policy отклоняет непроверенный ответ без скрытого повторного вызова; фактические расходы уже выполненных стадий сохраняются. SQLite хранит input/output/total tokens и доступные cached/reasoning usage, модель, тариф, стоимость каждого вызова и накопленный USD. Неизвестные usage или цена не превращаются в ноль; неполнота общей суммы видна в интерфейсе.

Финальная генерация основного чата использует `main_final_reasoning_effort = "low"` из `rag/config.toml`; фильтр, переписывание запроса и извлечение памяти используют `none`. Запрошенное значение и фактические reasoning tokens сохраняются в журнале. Инструменты остаются доступны для явно запрошенного внешнего исследования; справочные вопросы о проекте отвечаются по локальному контексту либо завершаются отказом.

## Проверки и оценка

```powershell
.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q tests tests_indexing tests_rag tests_evaluation
npm install --no-save playwright
npx playwright install chromium
node scripts/check-chat-rag-browser.cjs
```

Python тесты используют управляемые ответы провайдера. Browser fixture поднимает синтетический сервер и не отправляет запросы модели. Все десять оценочных вопросов рассчитаны на факты в текущем индексе; реальную проверку выполняет `scripts/evaluate_grounding.py` по инструкции в [evaluation/README.md](evaluation/README.md). Она требует API-ключ и сохраняет все попытки, источники и расходы. Программные проверки подтверждают структуру ссылок; содержательную опору каждого утверждения оценивают отдельно по полным фрагментам. Вопрос без ответа в базе проверяется отдельным сценарием.

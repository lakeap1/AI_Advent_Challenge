# День 32 — AI-ревью сервиса «Грани»

Контур качества учебного сервиса проверяет изменения кода, документов и базы знаний. Он получает настоящий diff Git, ищет связанный код и документы через Qwen embeddings и BM25/RRF, фильтрует контекст и передаёт его GLM. Принятый отчёт проходит программную проверку ссылок и один отдельный смысловой вызов общего валидатора сервиса.

Ревью работает на чтение: не исправляет файлы, не выполняет код PR и не делает merge. Обычный учебный чат остаётся основным сценарием сайта. Приложение и модели размещаются согласно [дню 31](../task_1/README.md); пользовательскому сайту не нужен локальный сервер.

## Возможности

- Добавления, изменения, удаления и переименования читаются из закреплённых Git objects. Незакоммиченные файлы не подставляются. Запрошенная base-ревизия сохраняется, а diff и исходная сторона контекста строятся от merge-base к head.
- Каждый источник несёт revision, path, blob OID, SHA256 и строки Git. Unicode-разделитель не считается переводом строки LF.
- Временный индекс PR отделён от production. Исходная и предложенная версии имеют разные source identities.
- GLM анализирует поведение, отказы, границы пользователей/веток/памяти, инварианты, RAG/MCP, расходы и противоречия документов с кодом. Находка содержит проблему, условия, последствия, основание и рекомендацию; гипотеза отличается от дефекта.
- Дополнительные RAG checks выбираются по влияющим путям и обеим сторонам rename. Изменённый алгоритм PR не исполняется: необходимая поведенческая проверка остаётся pending.
- Проверка использования источника включает короткий контрольный ответ в том же JSON генератора. Его буквальные цитаты проверяются программно, а смысл — тем же единственным semantic gate вместе с находками. Успешного поиска самого по себе недостаточно; неподтверждённое свойство остаётся pending.
- HTML показывает принятые находки, ревизии, проверки и расходы. Отклонённый черновик не публикуется; содержимое экранируется, JavaScript не используется.

## Требования и запуск

Python 3.12+, Git с поддержкой `--no-lazy-fetch`, доверенная общая библиотека `week_7/task_1/graphics`. Подготовка, механическая валидация и HTML-рендер используют стандартную библиотеку. Для AI установите зависимости из `requirements.txt`, явно включающего зависимости дня 31.

AI-этап выполняется на капсуле: `ZAI_API_KEY` остаётся в защищённом окружении сервера, Qwen доступен по loopback. Настройки, тарифы и бюджет берутся из `graphics.config.Settings`. Выбраны `glm-5.3-flash` и `qwen3-embedding:0.6b`, 1024 измерения. Вход PR не может менять эти параметры. Общая библиотека подключается явно из соседнего задания; `--service-root` позволяет администратору указать другую доверенную установку. Нельзя передавать checkout PR как runtime.

Команды выполняются из `week_7/task_2` в установленном окружении. Сначала создайте приватный каталог `data`. Замените `BASE_REVISION` и `HEAD_REVISION` настоящими commit/ref; объекты должны уже присутствовать локально.

```text
python -B -m pr_review prepare --repo ../.. --base BASE_REVISION --head HEAD_REVISION --related week_7/task_1/README.md --related week_7/task_1/docs/architecture.md --output data/preparation.json
python -B -m pr_review review --preparation data/preparation.json --data-dir data/reviews --run-key pr42-HEAD_REVISION --run-live --output data/review.json --html data/review.html
```

`--related` повторяется для необходимых окружающих файлов. Программа не делает checkout/reset/fetch; автоматическая догрузка partial clone отключена. Точечный `safe.directory` передаётся только в параметрах Git-процесса.

Настоящее AI-ревью требует явного `--run-live`. Отдельный `--data-dir` хранит постоянный журнал всех review-запусков и не должен пересекаться с производственным `GRAPHICS_DATA_DIR`. Один `run-key` означает одно событие с конкретным снимком: повтор возвращает сохранённый результат без повторного расхода; другой снимок с тем же ключом отклоняется. Незавершённый запуск не перезапускается автоматически. Существующие выходные файлы не перезаписываются.

Успех `prepare` означает только подготовку. Принятое AI-ревью имеет `status: accepted`, `review_accepted: true` и код выхода 0 у `review`. Остальные статусы, включая incomplete/rejected/error, не являются одобрением.

Для просмотра сохранённого результата без модели:

```text
python -B -m pr_review render --report data/review.json --output data/review-copy.html
```

## Проверки результата

Механический контракт находок доступен отдельно:

```text
python -B -m pr_review validate --preparation data/preparation.json --findings data/findings.json
```

Он проверяет schema version, base/head, уникальный ID, severity (`critical`, `high`, `medium`, `low`), kind (`defect`, `hypothesis`), обязательные описания, location и evidence. Место содержит revision/path/start_line/end_line, основание — source_id и буквальную quote. Pipeline дополнительно ограничивает цитаты реально показанным модели контекстом.

Отдельный `validate` проверяет самосогласованность предоставленного snapshot, не перечитывает Git и не аутентифицирует изменённый вручную файл. Его успех сохраняет `semantic_validation: not_run`, `review_accepted: false`. Смысловой валидатор рассматривает реальные изменения, источники и черновик. Принятие уменьшает риск ложного замечания, но не гарантирует полноту или абсолютную истинность ревью.

## Ограничения и расходы

Подготовка ограничена 200 изменёнными и связанными путями суммарно, 50 явно связанными путями, 128 КиБ на blob, 256 КиБ patch на файл, 2 МиБ исходных текстов, 4 МиБ patches, 4000 строк на источник, 8 МиБ вывода команды и 15 секундами на Git-команду. Входной и сериализованный выходной JSON CLI ограничены 8 МиБ. Переполнение и слишком глубокий JSON дают явную ошибку.

Известные чувствительные пути, базы, local runtime data, symlink, submodule, binary и невалидный UTF-8 исключаются. Это не универсальное доказательство отсутствия секретов в любом исходнике. Полный snapshot остаётся приватным и не включается в CI artifact.

RAG использует ограниченные фрагменты pinned sources, отдельные fingerprints, model digest и размерность. Внешние материалы вне переданного снимка не подмешиваются и не считаются проверенными. Неполное покрытие, неразрешённые зависимости корпуса и pending checks мешают полному принятию. Полный diff и выбранный контекст должны помещаться в операционный бюджет модели; слишком большой запрос отклоняется.

Embedding receipt сохраняет модель из ответа, фактическую размерность векторов и digest из `/api/tags` до и после запроса. Противоречие или отсутствие нужных метаданных останавливает принятие с сохранением доступного usage. Маркер `stable_tags_only` означает совпавшие наблюдения tags; он не доказывает digest весов конкретного ответа `/api/embed`.

Каждый embedding/LLM-этап имеет durable receipt и input/output policy. Input/output/total, cached input и reasoning берутся из доступного ответа. GLM-стоимость оценивается общим провайдером по сохранённому тарифу; reasoning не оплачивается дважды. Известная сумма, неполнота и неизвестная итоговая стоимость различаются. Списание bundle остаётся неизвестным. Отсутствие запроса не представляется измеренным нулевым расходом.

Все review runs используют одну постоянную базу и общий бюджет. Unknown usage после отправки блокирует следующие платные стадии и прогоны. Отклонение не стирает расход. Пользовательские история, профиль и память чата не изменяются.

## Автоматизация PR

В корне подготовлены `day32-review-request.yml` и `day32-ai-review.yml`: первый получает PR event без секретов и checkout; второй обрабатывает workflow_run доверенным кодом default branch. Он заново проверяет актуальные metadata PR, пропускает fork/draft/closed/stale, читает head только как Git objects и передаёт bounded JSON фиксированной SSH-команде капсулы. Actions закреплены SHA, checkout не сохраняет credentials.

Для активации файлы должны быть опубликованы в default branch, доверенный обработчик установлен, отдельный CI SSH-ключ ограничен forced command и настроены три repository secrets. Подробности — в [размещении](deploy/README.md). Ключ Z.ai в GitHub не передаётся. JSON/HTML результат доступен как CI artifact; неуспех не становится зелёным review.

Наличие файлов и успешный локальный replay не доказывают настоящий PR-trigger. До установки и реального GitHub run автоматизация подготовлена к активации. Старый `ci/pull-request-preparation.yml` — неактивный пример только подготовки контекста.

## Проверки и состав

```text
python -B -m unittest discover -s tests -v
```

Используйте окружение с зависимостями и явный `PYTHONPATH` на доверенный `week_7/task_1`; общие regression tests запускаются также из дня 31. Fake transport проверяет FSM, receipts, отказы и provenance, но не качество живого GLM/Qwen или доступность капсулы. Сетевые/model проверки включаются отдельно явным live-флагом. Для временных тестовых файлов задайте каталог на диске с достаточным местом.

`pr_review/` содержит Git reader, RAG impact/context, механический контракт, accounting/FSM, CLI, отчёт и CI/SSH обработчики; `tests/` — проверки, `deploy/` — фиксированный launcher и размещение. Приватные receipts и индексы хранятся в игнорируемом `data/`.

# День 18 — чат сводок по графике и арту через MCP

Отдельный чат «Сводки о графике» получает новые вопросы Computer Graphics, Graphic Design и Blender Stack Exchange за предыдущий календарный день по Омску. В нём можно выбрать сохранённую сводку и задавать вопросы по её материалам. Новые сводки не меняют контекст уже начатого обсуждения.

Одна сводка публикуется ежедневно в 00:00, часовой пояс Asia/Omsk (UTC+6), за завершившийся календарный день. Сервер собирает и агрегирует материалы без вызова модели. Cron на капсуле выполняет внутренний сбор в 00:00, 06:00, 12:00 и 18:00; дополнительные сборы не добавляют сообщения в чат. Сервер не зависит от браузера или локального компьютера. Создать сводку и получить историю можно любым клиентом MCP Streamable HTTP.

## Что попадает в сводку

До 100 новых вопросов за сутки из каждого выбранного сообщества, без фильтра по тегу. Сохраняются заголовки, короткие текстовые выдержки, теги, число ответов и ссылки. Это ограниченная выборка трёх сообществ, а не мониторинг всех сайтов о графике. Переполнение лимита и отсутствие вопросов отмечаются в выпуске. При временной ошибке источника выпуск ждёт повторной попытки; ошибка видна в журнале запусков. У вопроса есть составной идентификатор: сообщество и номер.

Сводка вычисляется кодом: количество вопросов, вопросы без ответов, частые теги и примеры материалов со ссылками. Обычные вопросы в чате сводки обрабатывает gpt-6-luna; ей передаются выбранная сводка и ограниченные выдержки, а не полные страницы или ответы авторов. В журнале видно число включённых вопросов.

Сохранены обычные диалоги помощника, профили, память, состояние задачи, инварианты, ветки и поиск Wikipedia/Stack Exchange через отдельный MCP. Новое обсуждение сводок не требует согласовывать учебный план. Код задания самостоятелен, без импортов соседних заданий.

## Локальное приложение

Python 3.11+. Из папки задания:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe app.py
```

Откройте http://127.0.0.1:5018 и выберите «Сводки о графике» слева. `OPENAI_API_KEY` в локальном `.env` нужен для ответов на ваши вопросы. Сбор и чтение сводок обходятся без ключа и вызова модели. Первый подсчёт контекста вопроса может загрузить словарь tiktoken, затем используется локальный кеш.

`DIGEST_MCP_URL` по умолчанию — `http://127.0.0.1:8018/mcp`, локальный конец SSH-туннеля к капсуле. Обычный поиск использует другой адрес: `KNOWLEDGE_MCP_URL=http://127.0.0.1:8017/mcp`.

```powershell
ssh -N -L 127.0.0.1:8018:127.0.0.1:8018 -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=yes -o ServerAliveInterval=30 -i <путь-к-ключу> <пользователь>@<капсула>
```

Если туннель недоступен, приложение показывает сохранённую историю с предупреждением. При восстановлении связи история догружается страницами без повторных записей. Связь нужна для новых сводок; вопросы по уже сохранённой сводке требуют только доступа к модели.

## MCP для другого клиента

Транспорт — Streamable HTTP, endpoint `/mcp`, SDK `mcp==2.2.0`. Сервер слушает loopback. Клиент подключается через SSH-туннель; на самой капсуле — непосредственно по `http://127.0.0.1:8018/mcp`.

| Инструмент | Параметры | Результат |
|---|---|---|
| `collect_digest` | нет | Получить или создать выпуск за предыдущий день; `executed`, `published`, `reason` |
| `run_scheduled_digest` | нет | Выполнить наступивший сбор / восстановить выпуск; `executed`, `published`, `reason` |
| `get_digest_state` | нет | Расписание, последние 20 запусков, последний суточный выпуск |
| `list_digests` | `after_run_id=0`, `limit=20` (1–100) | Только суточные выпуски по возрастанию номера, `next_cursor`, `has_more` |
| `get_digest` | `run_id` | Один сохранённый `digest` |
| `configure_digest` | `sources` — необязательный список | Включить фиксированное расписание |
| `pause_digest` | нет | Приостановить будущие сборы |

Разрешённые источники: `blender`, `computergraphics`, `graphicdesign`. Ручной запрос повторно возвращает уже готовый выпуск без нового обращения к источникам. `executed` означает факт сбора, `published` — создание суточного выпуска. `reason=already_published` означает возврат сохранённого выпуска; другие причины пропуска включают `not_due`, `paused`, `backoff` и `retry_wait`. Подтверждение настройки само по себе не является готовой сводкой.

Поле `digest_date` содержит дату выпуска в формате YYYY-MM-DD. `window_start` включён, `window_end` исключён: две полуночи по Омску. Дата уникальна, опубликованный снимок неизменен.

Встроенный клиент ограничивает страницу 20 сводками и синхронизирует по 5; прямой MCP допускает до 100.

В комплекте есть независимый консольный клиент, который выполняет настоящий MCP handshake и `call_tool`, без Flask:

```powershell
.\.venv\Scripts\python.exe scripts/digest_client.py get_digest_state
.\.venv\Scripts\python.exe scripts/digest_client.py collect_digest
.\.venv\Scripts\python.exe scripts/digest_client.py list_digests --after 0 --limit 5
.\.venv\Scripts\python.exe scripts/digest_client.py get_digest --run-id 1
```

Для собственной интеграции используйте `mcp.ClientSession`, `mcp.client.streamable_http.streamable_http_client`, затем `initialize()` и `call_tool()`. Структурированный ответ находится в `result.structured_content`; `result.is_error` нужно проверять до использования данных.

## Развёртывание и cron на капсуле

Скопируйте `digest_server/` и `deploy/` в `~/ai-advent-day18`. На Linux с systemd и установленным cron:

```sh
cd ~/ai-advent-day18
python3 -m venv .venv
.venv/bin/python -m pip install -r digest_server/requirements.txt
mkdir -p ~/.config/systemd/user
cp deploy/ai-advent-day18.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now ai-advent-day18.service
loginctl enable-linger "$USER"
sh deploy/install-cron.sh
```

Для linger могут потребоваться права администратора. Установщик сохраняет предыдущий crontab в `data/cron-backups/`, заменяет только свой именованный блок и допускает системный пояс UTC/Etc/UTC либо Asia/Omsk. На UTC-сервере набор часов 00/06/12/18 совпадает с нужными шестичасовыми сроками по Омску со сдвигом даты. Полночь Омска соответствует 18:00 UTC предыдущей даты; MCP отличает публикацию от остальных внутренних сборов. Пояс расписания и параметры публикации явно хранятся в MCP. Установщик не меняет системный часовой пояс.

Основной cron вызывает `python -m digest_server.cron_tick` в четыре заданных часа. Дополнительно он вызывает тот же MCP-инструмент на минутах 01, 06, 11, …, 56 и при загрузке капсулы. Проверка восстановления учитывает сохранённый срок, незавершённый суточный выпуск и паузу источника. Старого внутреннего цикла сбора в MCP-сервисе нет.

После установки включите расписание кнопкой в приложении или инструментом `configure_digest`. Первый recovery tick восстановит отсутствующий выпуск за последний завершившийся день, даже если старый внутренний сбор уже состоялся.

```sh
crontab -l
systemctl --user status ai-advent-day18.service --no-pager
loginctl show-user "$USER" -p Linger
sudo journalctl -t ai-advent-day18-cron -n 20 --no-pager
journalctl --user -u ai-advent-day18.service -n 20 --no-pager
systemctl --user restart ai-advent-day18.service
```

Для остановки сбора используйте `pause_digest`. Для остановки сервиса — `systemctl --user stop ai-advent-day18.service`; cron будет сообщать об отсутствии MCP, пока сервис не запущен. Полное отключение: удалите только блок `AI-ADVENT-DAY18` через `crontab -e` и выполните `systemctl --user disable --now ai-advent-day18.service`.

## Восстановление и хранение

Серверная база: `data/digest/digest.sqlite3`, путь меняется через `DIGEST_DATA_DIR`. Systemd перезапускает процесс при падении, Linger запускает пользовательский сервис независимо от SSH-сеанса. Межпроцессная блокировка запрещает два сервера с одной базой.

После перезапуска незавершённый запуск получает статус `interrupted`. Пропущенные слоты не воспроизводятся пачкой: восстанавливается выпуск только за последний завершившийся календарный день с исходными границами суток. Временная ошибка или пропущенный из-за backoff источник повторяется не раньше чем через 5 минут и не раньше срока API backoff; промежуточные попытки сохраняются в техническом архиве, в публичную ленту попадает только готовый выпуск. Публикация, завершение запуска и расписание фиксируются транзакционно. Ограничение в 100 вопросов само по себе не вызывает бесконечных повторов. После завершения срок снова календарный. Абсолютной гарантии «ровно один внешний GET» нет: авария после ответа API может потребовать повторного GET.

Клиентский аудит и зеркало: `data/digest-audit.sqlite3`. Вопросы и ответы: `data/profiles/<id>/daily-digest/digest-chat.sqlite3`. Выбор сводки сохраняется отдельно для каждого профиля. Сводки общие для локального оператора; профиль не является авторизацией. `CHAT_DATA_DIR` меняет локальный каталог. Базы не зашифрованы, исключены из Git, история автоматически не удаляется.

Перед обновлением остановите сервис и скопируйте код вместе с `data/digest/`; резервную копию храните вне каталога развёртывания. Для отката остановите сервис, восстановите согласованную пару кода и базы из копии, затем запустите сервис. Это восстановление из резервной копии, а не защита от потери диска: для последней нужны копии на другом носителе.

Работа 24/7 требует доступной капсулы, сети, API источников, диска и cron. MCP и Flask предназначены для loopback/доверенного туннеля; публичное многопользовательское размещение требует отдельной защиты.

## Политики и расходы

Сбор и агрегация не вызывают LLM и не требуют ключа на капсуле. Ключ в локальном приложении используется только при вопросе пользователя.

Сбор: `digest_server/policy.toml`; MCP-клиент: `agent/digest_policy.toml`; вопросы по сводке: `agent/digest_chat.toml`. Программно проверяются типы, объём, разрешённые источники, ссылки и агрегаты. Текст источников передаётся модели как недоверенные данные. Это не программная проверка истинности содержимого.

В чате сохраняются фактические input/output/total tokens, cached input и reasoning при наличии, стоимость запроса и накопленная USD-сумма, модель, режим обслуживания, тариф с источником и датой, результаты обеих политик. Reasoning уже включён в output. Неизвестный расход не превращается в ноль; сумма помечается неполной. Расход отклонённого ответа учитывается. Нет скрытого повторного вызова или автоматического платного восстановления вопроса после сбоя. Ответы запрашиваются обычным текстом без Markdown; MCP использует JSON.

```powershell
.\.venv\Scripts\python.exe -m pytest -q --basetemp=docs/test-temp -p no:cacheprovider
node tests/test_digest_ui.cjs
```

Тесты покрывают миграцию SQLite, календарные сроки, повторные cron ticks, восстановление, частичные ответы, backoff, настоящий локальный MCP-вызов, проверку клиента, зеркало, профили и учёт вопросов.
